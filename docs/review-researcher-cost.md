gate.test.mjs: 5/5 pass locally (node --test tests/gate.test.mjs).

## Findings (estimates, not measured: log meta.rows_written to confirm)
1. **Gate amplification.** A failed login does put() on two keys (ip + account), plus setAlarm and a later deleteAll per new key. Random login names make a new account Gate each, so one bad request costs several DO row writes. 100k bad requests/day could exhaust the DO SQL write pool. Gates fail open, so logins keep working, but Room alarms may share that pool (UNVERIFIED: does setAlarm count?). Fix: look up the user row first (cheap D1 read) and only touch the account Gate when the account exists; unknown names hit the IP Gate only. Responses stay identical.
2. **Successful logins are unthrottled.** Each success writes an events row (about 2-3 D1 rows with idx_events_user). Anyone with one valid account can loop /login: ~35k logins/day exhausts D1 writes and then registration, rename and ban all fail. Fix: soft cap per account, e.g. /hit ls:<login> 20/hour, and skip only the event insert when locked (login still succeeds).
3. **Register cost.** users row has PK autoindex + login + username_lc unique indexes = ~4 rows, plus events ~2-3. About 7 rows/registration, so MAX_REG_PER_DAY=300 uses ~2k rows/day: safe. Tradeoff to document: an attacker can burn the 300 daily slots and block real signups.
4. **Budget math for the guide:** Worker requests (100k/day) are the binding limit for anything anonymous; no code fix. If the user has a custom domain on Cloudflare, a free-plan rate-limiting rule on /login and /register in front of the Worker is the only real flood protection (workers.dev gets none).
